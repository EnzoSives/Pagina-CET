## Testing (`TESTING`)

> This stage is automatic: it is the agent's job, not the person's. Do not ask for an OK at each step; run it and report the result. If `human_present` is `true`, ask the person only about a doubt that changes the outcome (such as whether a failing test or the code is wrong). If it is `false`, run `orqen block` for such a doubt. The human review of the e2e comes later, in `QA_REVIEW` (full lane).

orqen already started the complete environment, ran the verification (the build and every configured test type: unit, integration, the full end-to-end regression, and visual), and shut it down. `test_result.level` says what verified it: `tests` (suites), `build` (it compiles, the project has no suites), `smoke` (only that the environment starts) or `none`. This is the only stage that runs the whole regression: development ran only the unit tests and the e2e of this change. See `test_result` and `environment`. The `scenarios` field lists the OpenSpec scenarios or, for the direct lane, the analysis acceptance criteria.

1. For each entry in `scenarios`, find the corresponding test and read its assertions to confirm the THEN behavior is covered.
2. Return one entry per item with the same `scenario` text, plus `covered` and `test` (`file::name`). `orqen complete` rejects missing entries.
3. If the suite failed, describe the probable cause in `failure_diagnosis` and give the developer actionable `suggestions`. Say whether each failure is in a test of this change or a regression in an unrelated test, and whether it looks flaky.
4. Set `coverage_ok: true` only when every scenario is covered.
5. If `test_coverage.uncovered` lists files, those tests (declared by this change) are not run by any suite in `orqen/environment.yaml`, so the regression above did not execute them. Do not add them yourself (the configuration is not part of a request): add the line to `suggestions` and tell the person which tests and that they have to be added to `tests` in `orqen/environment.yaml`. This is a warning: it does not fail the stage.
6. With `level` `build` or `smoke` there are no tests to point to: for each scenario set `covered: false` and write in `evidence` how it was checked instead (what the build or smoke confirmed and what the developer verified by hand, asking them if `human_present` is true). `coverage_ok: true` when every scenario has a test or evidence. Suggest adding tests in `suggestions`.
7. With `level` `none`, or `test_result.hint` saying the verification is below `verification.minimum`, there was nothing to verify with: this is an environment problem, not a code failure. Set up the verification as in "Environments and tests" of `AGENTS.md` (`/orqen:env`): with the person's OK configure `tests.build` or a suite, then run `orqen take <KEY> --agent tester` again. Without a person, block with the concrete proposal. When `hint` says the commands were only detected, offer to save them (`orqen env set`).
8. Leave the code as it is: in this stage only `orqen/environment.yaml` and `orqen/scripts/` may change, and only as in step 7.
